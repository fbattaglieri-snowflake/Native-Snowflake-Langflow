# ADR-003: Real Active Role Selector, SPCS Caller's Rights Boundary & Dual Identity Model

- **Status:** Accepted
- **Date:** 2026-10-17

## Context
In Snowpark Container Services (SPCS) caller's rights connections, executing `USE ROLE` after a connection has already been opened on behalf of the caller is not supported, and browser ingress sessions start with the user's default role (or `PUBLIC`). Furthermore, enabling `SECONDARY ROLES ALL` does not correspond to selecting a single active role and is explicitly prohibited.

## Decision
1. **Role Discovery & Per-Role Session Binding:** Discover roles granted to the authenticated user via `SELECT CURRENT_AVAILABLE_ROLES()`. When the user selects an active role in the topbar, open/renegotiate a role-scoped Snowflake session/token (`session:role:<ROLE>`) in a pool segregated by `(user_principal, active_role)` and verify `SELECT CURRENT_ROLE() = '<ROLE>'` on every execution.
2. **Prohibition of Silent Escalation:** Never enable `SECONDARY ROLES ALL` and never fall back silently to the SPCS service owner role.
3. **Dual Identity Model (`INTERACTIVE_CALLER` vs `TECHNICAL_AUTOMATION`):**
   - *Interactive execution:* operates exclusively under the authenticated user's identity and chosen active role.
   - *Technical automation (scheduled/M2M):* uses an explicitly configured minimum-privilege technical role for the approved flow, with zero automatic fallback from interactive to technical.
4. **Subsystem Identity Separation:** The active Snowflake role does not automatically become a PostgreSQL role on `:5432` nor does it alter `Cortex Search` *owner's rights* indexing semantics. `SnowflakeAuthzService` explicitly validates permissions for each target subsystem (`Snowflake SQL`, `Snowflake Postgres :5432`, `LLM Proxy`, `Cortex Search`) before invocation.

## Consequences
- Every operation executes under a verified `CURRENT_ROLE()` with deterministic cache invalidation (`context_epoch` increment) on role change or privilege revocation.
