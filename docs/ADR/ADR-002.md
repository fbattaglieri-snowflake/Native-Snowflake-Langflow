# ADR-002: Transactional Application Persistence (ORM) vs Analytical Snowflake Storage

- **Status:** Accepted
- **Date:** 2026-10-17

## Context
Langflow's application database (`SQLModel` / `SQLAlchemy` / `Alembic` in `services/database/service.py`) relies on low-latency OLTP transactions and row-level locking. Analytical Snowflake standard tables cannot serve as a drop-in replacement for the SQLAlchemy ORM, and placing SQLite on a Snowflake Stage fails with `disk I/O error` due to POSIX lock/WAL incompatibilities.

## Decision
1. **Production / Multi-Replica (Option A — Recommended):** Use a dedicated **Snowflake Postgres** instance (`CREATE POSTGRES INSTANCE <POSTGRES_INSTANCE> COMPUTE_FAMILY = 'STANDARD_M' STORAGE_SIZE_GB = 10 AUTHENTICATION_AUTHORITY = POSTGRES_OR_SNOWFLAKE`) connected over `:5432` with `sslmode=verify-ca` and `connect_timeout=10`.
2. **Single-Replica Development (Option B):** Use SQLite on a dedicated SPCS `block` storage volume (`>= 1 GiB`) paired with quiesced backups (`PRAGMA integrity_check` + SHA-256 verification) uploaded to `@<DATABASE>.<SCHEMA>.<STAGE_NAME>/backups/`.
3. **Strict Separation of Concerns:** The transactional ORM database remains strictly separate from analytical Snowflake tables used for `Flow Activity` trace replication (`<DATABASE>.<SCHEMA>.LANGFLOW_FLOW_RUNS`, `<DATABASE>.<SCHEMA>.LANGFLOW_FLOW_SPANS`), durable governance audit (`<DATABASE>.<SCHEMA>.LANGFLOW_AUDIT_LOG`), `Message History` on standard tables, and `Vector DB` stores (`Standard VECTOR`, `Hybrid VECTOR`, `Cortex Search`).

## Consequences
- Zero SQLite corruption on SPCS stages and full ACID guarantees for Langflow's internal state.
- Analytical SQL querying is provided via synchronized Snowflake tables.
